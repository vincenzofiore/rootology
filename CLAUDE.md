# Rootology

A personal assistant for vegetable gardens and small-scale agriculture, as a prototype for a few real users. Later it should grow into precision agriculture with field sensors.

The core idea comes from the original experiment (see `docs/experiment-log.md`):

- A **knowledge graph** holds verifiable facts, each with its source.
- An **LLM** (Claude) understands the question and phrases the answer, but never invents the facts and never chooses the answer values.
- A **calibrated decision layer** (Jev) decides from the facts with a real confidence, and knows when it does not know.
- A **human in the loop** answers the uncertain cases; who answered is recorded.
- A **quality suite** measures silent errors against an arbiter with known answers.

Sensors fit this design directly: missing and noisy readings are what the decision layer was built to handle (see the noise work in the experiment log).

## Working conventions

- Talk to the owner (Vincenzo) in Italian. Write all code, comments, commit messages, README and docs in English.
- Prototype for a few real users: keep it small, readable and easy to inspect, with no speculative abstractions. Real users mean real basics: their data is kept separate, secrets stay outside the repository, inputs from outside are validated, the app survives a failing external service.
- Never commit or push on your own; ask the owner each time. Commit messages are short, lowercase and imperative, and reference the GitHub issue (`refs #N`, `closes #N` on the last commit of an item). Work happens on `develop`; `main` is updated only by the owner.
- The quality suite is ground truth: do not change `OntologyDefinition` (now the suite's fixture), the five cases, the recorded judgments under `src/test/resources/experiments/` or `ExperimentRecordingTest`, unless explicitly asked. The real knowledge base grows elsewhere (see the plan).
- Jev is the decision layer by design. Do not build a Jev-vs-LLM comparison of decision layers.
- This domain is deliberately unrelated to the owner's day job. Do not import concepts or code from any professional project.
- Before adding a dependency or an external data source, check its current version, compatibility and license, and report to the owner.

## Current state (already built)

- Stack: Spring Boot 4.1.0, Java 25, Maven (`./mvnw`), Spring Modulith 2.1.0 (boundaries verified by `ModularityTest`, which must keep passing), Apache Jena 6.2.0, Embabel 1.5.4 (`embabel-agent-starter-anthropic`, default LLM `claude-sonnet-5-5`), Vaadin Flow 25.3, Spring Security OAuth2 client, Postgres 17 with Flyway, Neo4j 2026.10 (Java driver, Cypher). Some Initializr leftovers remain (actuator, cache, restdocs; see #10).
- Modules (base package `io.github.vincenzofiore.rootology`):
  - `ontology`: `OntologyDefinition`, the original closed dataset (3 plants, 3 pests). Now the quality suite's fixture.
  - `inference`: Jena graph and SPARQL queries. Serves only the arbiter of the quality suite.
  - `facts`: the pipeline's fact store in Neo4j, which holds two graphs that never mix: the quality suite's dataset (label `Suite`, from `OntologyFacts.from(OntologyDefinition)`, read by `FactSource.allFacts()`) and the curated knowledge base (#16, label `Kb`: `Crop`, `Family`, `Organism`, `Zone`, `Source`; relationships `BELONGS_TO`, `COMPANION_OF`, `ANTAGONIST_OF`, `AFFECTS`, `WINDOW`, each with the ids of its sources; read by `KnowledgeGraph`). `FactGraphLoader` rebuilds both at startup: it reads the curated files (`CuratedKnowledgeReader`) and runs `KnowledgeValidator` first, and the app does not start if the knowledge base is invalid (unknown references, sources without commercial use, values out of range, contradicting pairs). Inference rules (#16), each with an id and tests, and their results always tagged `INFERRED` with the rule: `ZoneShiftRule` (`zone-shift-v1`: NORD/SUD windows from CENTRO, by season, winter harvests not derived, a curated window always wins) and `RotationRule` in `garden` (`family-rotation-v1`: warns when a crop follows one of the same family in a plot). Companion pairs are never reversed. `KnowledgeGraph.resolve` finds a crop or organism by id, Italian, English or scientific name; `factsAbout(name)` gives its facts in the question's language (subject kept exactly as asked), each as a `SourcedFact` with its source ids: declared companions/antagonists, `affects`, and `activeInSeason` from the pest months. `SourceCatalog` exposes `sources.csv`. `CropCatalog` loads the approved crops from the curated file `src/main/resources/knowledge/crops-v1.csv` (39 crops: id, Italian, English and scientific names, family checked against Wikidata, Wikidata and FAO ECOCROP ids). Curated knowledge files (#16) live in `src/main/resources/knowledge/`: `sources.csv` (every source with license; only commercial-use sources), `crop-needs.csv` (FAO ECOCROP, imported by the `live-api` tool `EcocropImportTool`), `sowing-windows.csv` (CENTRO zone, editorial, `verified=no`), `crop-pairs.csv` (66 companion and antagonist pairs with an evidence level: study, extension or traditional; declared in one direction, never reversed), `pests.csv` (24 pests and diseases identified by EPPO codes) and `pest-hosts.csv` (affected crops and months, editorial, `verified=no`). Human-readable versions: `docs/crops-v1.md`, `docs/crop-pairs-v1.md`, `docs/pests-v1.md`. `KnowledgeValidatorTest` covers the validator, `KnowledgeGraphTest` the loaded graph.
  - `decision`: `Intent` + `QueryKind`, `GraphFacts` (readings tagged CURATED / UNCONFIRMED / INFERRED, with source ids and, for inferred ones, `derivedBy`; Jev gets the INFERRED description only when an inferred reading is present, so suite requests are unchanged), `Decision`, interface `DecisionLayer`. `JevDecisionLayer` (TypeSafe System One API, structured state with fixed field order, `MIN_CONFIDENCE` 0.5) when `ROOTOLOGY_TYPESAFE_API_KEY` is set, otherwise `StubDecisionLayer`; `SkepticalStubDecisionLayer` as a baseline.
  - `pipeline`: Embabel agent `GardenPipelineAgent` (Question -> Intent via Claude -> GraphFacts -> Decision -> Resolution -> PipelineAnswer, phrased by Claude). `GardenPipeline.ask(...)` never blocks (`ReviewMode.AUTOMATIC`); `start(question, noise, RunContext)` / `pending(spaceId)` / `respond(processId, spaceId, answer)` pause on escalation until a member of the run's space answers (`ReviewMode.HUMAN`). `NoisyFacts` / `NoiseProfile` degrade inputs for the suite. `FactScope` on the blackboard chooses the graph: `SUITE` (default: comparisons, recordings, `start`) or `KNOWLEDGE_BASE` (`GardenPipeline.askKnowledgeBase`, real questions). `PipelineAnswer.sources` lists the source ids of the facts behind the answer. Question kinds (#17): the suite's four plus `ANTAGONISTS`, `SOWING_TIME`, `HARVEST_TIME`, `SOW_NOW` on the knowledge base, and `GROWING_NOW`, `PEST_RISK`, `SOW_IN_PLOT` on the asking space's garden (`GardenFacts`: `grows`, `threatens`, and `avoidIn` inferred by `family-rotation-v1`; source id `garden`; `RunContext` is on the blackboard, `RunContext.NONE` for suite runs). The zone comes from the question, else the garden's latitude (`GardenService.zone`: ≥44° N NORD, ≥41.5° N CENTRO, else SUD), else CENTRO; `Intent` also carries `language` (names and answer in the question's language; never sent to Jev), `zone` (NORD/CENTRO/SUD, default CENTRO) and `month` (SOW_NOW, default the current month in Italy). Windows from `zone-shift-v1` reach Jev as INFERRED readings.
  - `experiments`: the quality suite's arbiter (`ExperimentRunner`), the five cases (`ExperimentCase`), recorded answers and comparison records.
  - `spaces` (#15): `app_user`, `space`, `space_member` (`OWNER` / `MEMBER`), Flyway `V2__create_spaces.sql` and `V3__track_first_login.sql`. GitHub logins are stored and compared in lower case (`SpaceService.normalizeLogin`). `SpaceService.signedIn` (called on every login) creates the person's personal space on their first real login (`first_login_at`), also when someone had already added them to a space; `spacesOf`, `isMember`, `membersOf`, `addMember`, `removeMember` (owners remove, members leave; nobody leaves their personal space, `space.personal_of`; a space keeps at least one owner), `changeRole`. Personal data elsewhere refers to a space by id.
  - Invitations (#23, `InvitationService`, Flyway `V4`): an owner creates a single-use link (`/invite/<token>`, 7 days, optionally restricted to one GitHub login); only the token's SHA-256 is stored; owners list and revoke pending ones. The invitation page is public: the token waits in the HTTP session (`PendingInvitation`) through the GitHub login, and `AllowListOAuth2UserService` accepts it. Who may sign in: the bootstrap `ROOTOLOGY_ALLOWED_GITHUB_USERS`, anyone who already belongs to a space, or the holder of a valid invitation.
  - `garden` (#14, Flyway `V5`): gardens of a space (name, town, coordinates rounded to 0.01 degrees), plots (`GROUND`, `RAISED_BED`, `CONTAINER`; soil incl. `POTTING_MIX`; optional area), plantings (crop from `CropCatalog`, sown or transplanted, date, ended when harvested). `GardenService` checks membership on every call; `growingOn(space, login, day)` is the context for garden questions (#17). UI: Garden view.
  - `enrichment` (#24, Flyway `V6`, `V7`): members propose missing facts (`facts.Contribution`: another name for a crop or organism, a companion/antagonist pair, a pest on a crop with months). Scope `SPACE` applies at once and only to that space (Neo4j relationships and `Alias` nodes carry `spaceId`; readings tagged `PROPOSED`, a source description sent to Jev only when present); scope `GLOBAL` needs a cited source and a curator's approval (`ROOTOLOGY_CURATORS`, comma-separated GitHub logins), then reaches everyone as curated. `KnowledgeContributions` (in `facts`) checks proposals with the curated files' rules and writes them; proposals and reviews stay in Postgres (`knowledge_proposal`, statuses PENDING / APPROVED / REJECTED / WITHDRAWN) and approved ones are rewritten after every graph rebuild (`KnowledgeGraphLoaded`). Source ids `proposal-<id>`. Global reads of `KnowledgeGraph` never see space facts. UI: Knowledge view (propose, this space's history, withdraw, curator queue) and a "Propose the missing fact" link on Ask escalations. Claude suggestions are not built yet.
  - `weather` (#18, Flyway `V8`): the public forecast of MET Norway (Locationforecast 2.0 compact, CC BY 4.0 / NLOD, commercial use allowed, "Data from MET Norway"; User-Agent identifies the app; `Expires` and `If-Modified-Since` respected) for the space's first garden with coordinates, cached in Postgres (`weather_location`, `weather_hour`; past hours kept 30 days as an estimate of the recent past until #21). `WeatherService.around` never blocks an answer: short timeouts, a copy up to 24 h old is used as stale, otherwise no weather. Rules: `frost-risk-v1` (forecast minimum over 7 days within 1 °C of ECOCROP's killing temperature for young plants, `temp_kill_early` in `crop-needs.csv`, known for 19 of 38 crops; unknown ones are named in a note, never guessed) gives `(crop, avoidNow, frost)` for `SOW_NOW` / `SOW_IN_PLOT`; `smith-period-v1` (two days with minimum ≥ 10 °C and ≥ 11 h of RH ≥ 90 %, from two days ago to three days ahead) gives `(Late blight, favouredByWeather, crop)` for `PEST_RISK` on tomato and potato. Only for questions about the current month. Readings tagged `FORECAST` (described to Jev only when present); `GraphFacts.notes` and `PipelineAnswer.notes` tell the person what was used or missing (never sent to Jev; added to Claude's phrasing prompt only when present). No coordinates means no weather, with a note. Weather Underground was ruled out: its PWS key is for personal, non-commercial use only.
  - `resilience` (#29): `CircuitBreaker` (3 consecutive failures open it for 2 minutes, then one trial call) and `ServiceUnavailableException`. Every external call fails fast: MET Norway (3 s connect, 5 s read; open circuit means stored copy or no weather), Jev (3 s connect, 20 s read; failure or open circuit escalates to a person), Claude (`ClaudeCircuit`: understanding fails at once with a clear message, phrasing falls back to a plain sentence with the values and notes; Embabel's Anthropic retries cut to 3 attempts with 1-4 s backoff, prompt timeout 30 s). Embabel retried every failing action 5 times over minutes: `embabel.agent.platform.action-qos.default.max-attempts: 1` (the agent-level `actionRetryPolicy = FIRE_ONCE` had no effect in 1.5.4).
  - `geocoding` (#30): `GeoNames` searches places by the start of their name (`searchJSON`, populated places, 3+ letters, LRU cache) and the nearest populated place to a position (`findNearbyPlaceNameJSON`: town, region, country), on `secure.geonames.org` with a free account (`ROOTOLOGY_GEONAMES_USERNAME`; empty disables place search). CC BY 4.0, commercial use allowed, 10,000 credits a day; errors come in the body (`status`; 15 = no result, not a failure) and go through a `CircuitBreaker`. The Garden dialog fills town, coordinates and country from a found place, or coordinates plus the nearest town and its country from the browser's position (`navigator.geolocation`, HTTPS or localhost only); typed coordinates get a missing town or country from the nearest place on save; saving never depends on GeoNames. `garden.country_code` (Flyway `V9`): zones and sowing calendars apply to gardens in Italy only (no country = saved before #30 = Italy); abroad the zone is `GardenService.OUTSIDE_ITALY`, calendar questions escalate with a note, the weather still works. GeoNames and Nominatim were compared; Nominatim forbids autocomplete; a local GeoNames copy was judged too heavy for a rare operation.
  - `history`: finished UI runs stored in Postgres (`pipeline_run`, Flyway migrations, Hibernate `ddl-auto: validate`), with the arbiter's answer when the question is a suite case. Each run belongs to a space (`space_id`) and records who started it; `RunHistory.recent(spaceId)`. Runs stored before #15 have no space and are not shown.
  - `ui` (Vaadin, http://localhost:8080): Ask (free questions on the knowledge base, with sources), Garden, Compare, Escalations, History, Space, and a public Sources page (licences and attribution, from `sources.csv`) (members; owners add people by GitHub login); a space switcher in the navbar. `CurrentUser` (Vaadin session scope) is the only source of the signed-in login and current space. GitHub OAuth2 login with an allow-list (`ROOTOLOGY_ALLOWED_GITHUB_USERS`), which works as invite-only access for the prototype.
- Secrets and settings come from project-specific environment variables: `ROOTOLOGY_ANTHROPIC_API_KEY`, `ROOTOLOGY_TYPESAFE_API_KEY`, `ROOTOLOGY_GITHUB_CLIENT_ID`, `ROOTOLOGY_GITHUB_CLIENT_SECRET`, `ROOTOLOGY_ALLOWED_GITHUB_USERS`, `ROOTOLOGY_CURATORS`, `ROOTOLOGY_GEONAMES_USERNAME` (never `ANTHROPIC_API_KEY`, which Claude Code itself would pick up).
- `./mvnw spring-boot:run` starts Postgres and Neo4j from `compose.yaml` (needs Docker). Spring tests import `TestcontainersConfiguration`. A plain `./mvnw test` makes no paid call; tests tagged `live-api` call Claude and Jev and run with `-Plive`.
- CI (#13): `.github/workflows/build.yml` runs `./mvnw test` on every push to `develop` and `main` and on pull requests, on a pinned `ubuntu-26.04` runner with Java 25 (Temurin); no secrets, Testcontainers uses the runner's Docker. The README badge shows the `develop` status.
- `.claude/skills/rootology-garden-companion/SKILL.md` is the prose version of the original dataset, used only by the experiment's "Claude with skill" arm.

## Roadmap

Each item is a GitHub issue on `vincenzofiore/rootology` (labels `plan` and `phase-1` / `phase-2`), listed in working order. The issue is the detailed plan; this list only orders it.

Phase 0, done 2026-11-03: reframe from toy experiment to prototype (this file, `docs/experiment-log.md`, the issue list; #8 closed as no longer needed).

Phase 1, a personal assistant for a few invited users:

1. #13 (done) CI with GitHub Actions (offline build on every push).
2. #15 (done) Shared spaces: `app_user`, `space`, `space_member` (`OWNER` / `MEMBER`); a personal space created on first login; runs and escalations owned by a space, with who did what recorded; a current-space switcher; owners add members by GitHub login. The space filter lives in services and repositories, from a single `CurrentUser`.
3. #23 (done) Invitations to a shared space, and removing members: single-use expiring links (tokens stored hashed), revocable; accepting one also lets that GitHub account in, so the allow-list moves to the database. No email in the first version.
4. #14 (done) My garden: plots, crops, coarse location and soil, owned by a space.
5. #16 (done) Knowledge base v1: real crops, with a source and license for every fact, and an ontology layer designed with the data: a light schema in Neo4j (classes, hierarchies, constraints), AGROVOC identifiers where they fit, explicit and tested inference rules, inferred facts tagged `INFERRED`. Choose the sources with the owner first.
6. #24 (done) Knowledge enrichment: members propose missing facts (names, crops, varieties, pairs, windows) with a source; a curator approves global facts; space-level facts stay in their space; Claude may suggest, never write. Sources and the crop list: `docs/knowledge-sources.md`, `docs/crops-v1.md` (commercial use is a goal, so no non-commercial sources).
7. #17 (done) New question types (what to sow now, what not to plant together, pest risk this week, when to harvest).
8. #18 (done) Local weather from MET Norway, with the frost and Smith period rules.
9. #29 (done) Fail fast on external services: short timeouts on every client and a minimal circuit breaker per service (no new dependency; Resilience4j later with #27).
10. #30 (done) Garden coordinates from the town name (Nominatim/OpenStreetMap, policy checked first) or the browser's geolocation; rounded to 0.01 degrees; saving never blocked by the geocoder.
11. #20 Quality suite: golden questions in CI, failing on silent wrong answers.
12. #19 Usage limits per user for Claude and Jev.
13. #25 Send email: SMTP (Gmail app password or a transactional service, terms checked first), Mailpit in development, invitations by email bound to a verified address.
14. #26 Notifications: in-app and email, starting with escalations; per-person preferences; Telegram, web push or ntfy later for sensors.
15. #27 Observability: structured logs, domain metrics (escalation rate, confidence, Claude/Jev latency and errors, cost per user), traces through the agent, health checks, alerts; no personal data in logs or traces.
16. #31 UX v1: typed notes instead of strings, a weather card (7 days, frost days, MET Norway icons), answers as cards (values, confidence, warnings, sources), a garden home, Italian UI, usable on a phone.
17. #12 Deploy (likely a small cloud server; the DS225+ NAS would need 6 GB RAM): invite-only (allow-list and invitations, #23), HTTPS behind the platform, Postgres backups.
18. #28 Sign in with Google and provider-independent identities (verified email), once the deployment has a domain name.
19. #10 Trim unused Initializr dependencies. #4 Jev client library (deferred, see Open questions).

Phase 2, precision agriculture (umbrella #22):

1. #21 The owner's weather station on their terrace as the first real sensor and test bed: ingest its readings, show them next to the forecast, feed one decision (for example frost or watering), treat gaps and outliers as uncertain readings. Model sensors and readings on SOSA/SSN (W3C).
2. Then split #22: field sensors (soil moisture and temperature) as time series with per-sensor reliability, and operational decisions (irrigation, disease risk) that escalate when readings are missing or uncertain. #9 (Embabel DICE, confidence-weighted propositions) may fit here.
