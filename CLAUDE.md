# Rootology

A personal assistant for vegetable gardens and small-scale agriculture, as a prototype for a few real users. Later it should grow into precision agriculture with field sensors.

The core idea comes from the original experiment (see `docs/experiment-log.md`):

- A **knowledge graph** holds verifiable facts, each with its source.
- An **LLM** (Claude) understands the question and phrases the answer, but never invents the facts and never chooses the answer values.
- A **calibrated decision layer** (Jev) decides from the facts with a real confidence, and knows when it does not know.
- A **human in the loop** answers the uncertain cases; who answered is recorded.
- A **quality suite** measures silent errors against an arbiter with known answers.

Sensors fit this design directly: missing and noisy readings are what the decision layer was built to handle (see the noise work in the experiment log).

## Working conventions

- Talk to the owner (Vincenzo) in Italian. Write all code, comments, commit messages, README and docs in English. URLs, route segments and query parameters are always English, never Italian words.
- Prototype for a few real users: keep it small, readable and easy to inspect, with no speculative abstractions. Real users mean real basics: their data is kept separate, secrets stay outside the repository, inputs from outside are validated, the app survives a failing external service.
- Never commit or push on your own; ask the owner each time. Commit messages are short, lowercase and imperative, and reference the GitHub issue (`refs #N`, `closes #N` on the last commit of an item). Work happens on `develop`; `main` is updated only by the owner. A change that people or the server notice gets a line in `CHANGELOG.md` under `[Unreleased]` (Keep a Changelog, in English, with the issue number); internal refactors and tests do not.
- The quality suite is ground truth: do not change `OntologyDefinition` (now the suite's fixture), the five cases, the recorded judgments under `src/test/resources/experiments/` or `ExperimentRecordingTest`, unless explicitly asked. The real knowledge base grows elsewhere (see the plan).
- Jev is the decision layer by design. Do not build a Jev-vs-LLM comparison of decision layers.
- This domain is deliberately unrelated to the owner's day job. Do not import concepts or code from any professional project.
- Design matters as much as function: the app must be easy to use, easy to understand at a glance and look like a modern application. Prefer a clear icon with a value or a count over a sentence (the word stays as tooltip and aria label, so nothing is lost for screen readers), show only what helps the decision at hand, keep the same icon and pattern for the same action everywhere (`ui.RowActions`), confirm before anything destructive, and check every screen on a phone, in dark mode and with a keyboard. Styles live only in `styles/rootology.css`. When a screen feels crowded or wordy, propose a simpler one.
- Before adding a dependency or an external data source, check its current version, compatibility and license, and report to the owner.

The unused Initializr starters (cache, validation, REST Docs with Asciidoctor, the Modulith actuator endpoint) went in #10; Spring Cache was dropped because nothing needs it (GeoNames, weather, Telegram and the curated files keep their own copies).
- Modules (base package `io.github.vincenzofiore.rootology`):
  - `ontology`: `OntologyDefinition`, the original closed dataset (3 plants, 3 pests). Now the quality suite's fixture.
  - `inference`: Jena graph and SPARQL queries. Serves only the arbiter of the quality suite.
  - `facts`: the pipeline's fact store in Neo4j, which holds two graphs that never mix: the quality suite's dataset (label `Suite`, from `OntologyFacts.from(OntologyDefinition)`, read by `FactSource.allFacts()`) and the curated knowledge base (#16, label `Kb`: `Crop`, `Family`, `Organism`, `Zone`, `Source`; relationships `BELONGS_TO`, `COMPANION_OF`, `ANTAGONIST_OF`, `AFFECTS`, `WINDOW`, each with the ids of its sources; read by `KnowledgeGraph`). `FactGraphLoader` rebuilds both at startup: it reads the curated files (`CuratedKnowledgeReader`) and runs `KnowledgeValidator` first, and the app does not start if the knowledge base is invalid (unknown references, sources without commercial use, values out of range, contradicting pairs). Inference rules (#16), each with an id and tests, and their results always tagged `INFERRED` with the rule: `RotationRule` in `garden` (`family-rotation-v1`: warns when a crop follows one of the same family in a plot). The sowing, planting and harvest calendars are rules on the curated files, not Cypher reads (#62): `ClimateCells` + `ClimateCellsReader` load `climate-cells-v1.csv.gz` (AgERA5 1996–2025 frost dates, growing season, land elevation and land fraction per 0.1° land cell of Europe, as compact primitive arrays); `KnowledgeValidator.validateCells` stops startup on a bad file; `FrostSeasonRule` (`frost-season-v1`) gives a `SiteProfile` its two safe months from `last_frost_p80` and `first_frost_p20`, after the altitude correction (6.5 °C/km, 0.15 °C/day, capped at 500 m, skipped on a coast with land fraction below 0.9 and when the altitude is missing or -9999); `ReferenceSite` gives the site of a zone named in the question (NORD = Milan, CENTRO = Vasto, SUD = Palermo, cell values with no correction); `FrostShiftRule` (`frost-shift-v1`) moves Vasto's curated CENTRO windows only where the site's safe months make them impossible, by crop `frost_group` (TENDER, HARDY, AUTUMN, OVERWINTER, LONG), never earlier in spring than Vasto, never reversing a window, year-round windows unchanged and winter harvests not derived when their shift is not 0; a window that cannot be derived is not a window, so the question escalates. `ClimateWindows` serves the derived windows and facts (with `rootology-editorial`, `agera5`, `copernicus-dem-90m`, plus `geonames-gtopo30` when the altitude was used); the curated NORD/SUD rows apply only when the question names that zone, and then win over the derived window of the same crop and activity; Vasto itself (CENTRO named, or the default outside a garden) gets its curated rows, not inferred ones. The Sources page shows the AgERA5, Copernicus DEM and GTOPO30 notices. `KnowledgeGraphLoader` writes curated windows only. Companion pairs are never reversed. `KnowledgeGraph.resolve` finds a crop or organism by id, Italian, English or scientific name; `factsAbout(name)` gives its facts in the question's language (subject kept exactly as asked), each as a `SourcedFact` with its source ids: declared companions/antagonists, `affects`, and `activeInSeason` from the pest months. `SourceCatalog` exposes `sources.csv`. `CropCatalog` loads the approved crops from the curated file `src/main/resources/knowledge/crops-v1.csv` (39 crops: id, Italian, English and scientific names, family checked against Wikidata, Wikidata and FAO ECOCROP ids, and `frost_group` for #62). `climate-cells-v1.csv.gz` is the climate profile file; `docs/climate-profile.md` describes it and how `tools/climate` makes it. Curated knowledge files (#16) live in `src/main/resources/knowledge/`: `sources.csv` (every source with license; only commercial-use sources), `crop-needs.csv` (FAO ECOCROP, imported by the `live-api` tool `EcocropImportTool`), `sowing-windows.csv` (the CENTRO rows are Vasto's, the base of `frost-shift-v1`, editorial, `verified=no`; the one curated NORD row applies only when the question names NORD), `crop-pairs.csv` (66 companion and antagonist pairs with an evidence level: study, extension or traditional; declared in one direction, never reversed), `pests.csv` (24 pests and diseases identified by EPPO codes) and `pest-hosts.csv` (affected crops and months, editorial, `verified=no`). Human-readable versions: `docs/crops-v1.md`, `docs/crop-pairs-v1.md`, `docs/pests-v1.md`. `KnowledgeValidatorTest` covers the validator, `KnowledgeGraphTest` the loaded graph.
  - `decision`: `Intent` + `QueryKind`, `GraphFacts` (readings tagged CURATED / UNCONFIRMED / INFERRED, with source ids and, for inferred ones, `derivedBy`; Jev gets the INFERRED description only when an inferred reading is present, so suite requests are unchanged; the site's climate profile is never sent to Jev: the derived windows already account for its frost dates, and the dates made Jev doubt them, #62), `Decision`, interface `DecisionLayer`. `JevDecisionLayer` (TypeSafe System One API, structured state with fixed field order, `MIN_CONFIDENCE` 0.5) when `ROOTOLOGY_TYPESAFE_API_KEY` is set, otherwise `StubDecisionLayer`; `SkepticalStubDecisionLayer` as a baseline. Domain filter (#53): interface `DomainFilter`, `JevDomainFilter` (one Noul question, `is_garden_question`, on the question text alone as `state`, with `true`/`false` criteria; `REFUSE_BELOW` 0.15, a first value to review after the first live run) and `PassThroughDomainFilter` when no key is set. It decides whether a question is about vegetable gardens and small-scale growing; only a clear no is refused, and every failure (open circuit, error, timeout) lets the question through.

The fixed text is `ask.offdomain` in the UI's language (no Claude call detected the question's), with `ask.offdomain.anyway` for the button. `PipelineAnswer.sources` lists the source ids of the facts behind the answer. Process ids are random UUIDs (`ProcessIdConfiguration`, `@Primary` `AgentProcessIdGenerator`, #61): Embabel's default draws a repeated "moby" name, and we key waiting questions, notifications and history by the id. Question kinds (#17): the suite's four plus `ANTAGONISTS`, `SOWING_TIME`, `HARVEST_TIME`, `SOW_NOW` on the knowledge base, and `GROWING_NOW`, `PEST_RISK`, `SOW_IN_PLOT` on the asking space's garden (`GardenFacts`: `grows`, `threatens`, and `avoidIn` inferred by `family-rotation-v1`; source id `garden`; `RunContext` is on the blackboard, `RunContext.NONE` for suite runs).
  Question context (#55): one resolver, once per run, between understanding and the facts. The `ContextResolver` action gives a `QuestionContext` (internal to the pipeline) — the run's garden, the climate profile of the site its calendars read, the plot a `SOW_IN_PLOT` question names, the place of the forecast, the effective `Intent` and the context notes — and every part reads it: `GardenFacts`, `WeatherFacts`, `LightFacts`, the decision layer and the answer. Precedence for the calendar kinds (sowing and harvest windows, `SOW_NOW`, `SOW_IN_PLOT`): a zone the question names uses that zone's reference site (`ReferenceSite`), otherwise the run's garden uses its own `SiteProfile` from its coordinates and altitude, otherwise the default is Vasto (CENTRO). `GardenService.zone` (≥44° N NORD, ≥41.5° N CENTRO, else SUD, `OUTSIDE_ITALY` abroad) is now only for the note that says the question names another zone than the garden's, and for a garden abroad with no profile; it no longer chooses the calendar. A garden abroad with a profile gets its derived windows and the `WINDOWS_FROM_CLIMATE` note; `OUTSIDE_ITALY` stays only for a garden abroad with no profile. A pest question (`PEST_RISK`) gets the month and no calendar, since the pest months and the weather apply abroad too (#58). The month is the question's, or the current month in Italy. Only the run's garden is read: nothing in the pipeline chooses a garden any more (no `findFirst` over gardens or plots). A plot is looked up in that garden only, and a plot not found or matching several, a garden question asked outside a garden (`GROWING_NOW`, `PEST_RISK`, `SOW_IN_PLOT`) and a garden deleted between opening the page and asking escalate before the decision layer, without a Jev call, with a note that says the specifics (`reason.needsgarden`, `reason.gardengone`, `reason.plot`). Windows from `frost-shift-v1` reach Jev as INFERRED readings with their site's sources; the knowledge base's calendar rules tell Jev the facts are already those of the question's site.
