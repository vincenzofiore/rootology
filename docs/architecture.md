# Architecture and current state

What is built, module by module, with the issue that built it. Moved verbatim from CLAUDE.md (#128): read the
part the work touches. The module boundaries are checked by `ModularityTest`, which also writes the module
diagram and each module's dependencies to `target/spring-modulith-docs/` (`components.puml`, `module-*.adoc`).
The project's conventions are checked by `ArchitectureTest` (#150): "now" and the time zone only from the `Clock`
bean, no `getStyle()` in the UI, the UI only through services, the quality suite isolated from the real
knowledge base, a circuit breaker on every external HTTP call, no `System.getenv`, no standard streams,
`printStackTrace` or field injection, `java.util.Random` only in `NoisyFacts`. Violations that existed when a
rule came in are frozen in `src/test/resources/archunit-store` (ArchUnit's `FreezingArchRule`): only new ones
fail, and the store shrinks as they are fixed. A new rule's store is created once by hand
(`freeze.store.default.allowStoreCreation=true` in `archunit.properties`, then back to `false`).

- Stack: Spring Boot 4.1.3, Java 25, Maven (`./mvnw`), Spring Modulith 2.1.2 (boundaries verified by `ModularityTest`, which must keep passing), Apache Jena 6.2.0, Embabel 1.5.4 (`embabel-agent-starter-anthropic`, default LLM `claude-sonnet-5-5`), Vaadin Flow 25.3, Spring Security OAuth2 client, Postgres 17 with Flyway, Neo4j 2026.10 (Java driver, Cypher). The unused Initializr starters (cache, validation, REST Docs with Asciidoctor, the Modulith actuator endpoint) went in #10; Spring Cache was dropped because nothing needs it (GeoNames, weather, Telegram and the curated files keep their own copies).
- Modules (base package `app.rootology`):
  - `ontology`: `OntologyDefinition`, the original closed dataset (3 plants, 3 pests). Now the quality suite's fixture.
  - `inference`: Jena graph and SPARQL queries. Serves only the arbiter of the quality suite.
  - `facts`: the pipeline's fact store in Neo4j, which holds two graphs that never mix: the quality suite's dataset (label `Suite`, from `OntologyFacts.from(OntologyDefinition)`, read by `FactSource.allFacts()`) and the curated knowledge base (#16, label `Kb`: `Crop`, `Family`, `Organism`, `Zone`, `Source`; relationships `BELONGS_TO`, `COMPANION_OF`, `ANTAGONIST_OF`, `AFFECTS`, `WINDOW`, each with the ids of its sources; read by `KnowledgeGraph`). `FactGraphLoader` rebuilds both at startup: it reads the curated files (`CuratedKnowledgeReader`) and runs `KnowledgeValidator` first, and the app does not start if the knowledge base is invalid (unknown references, sources without commercial use, values out of range, contradicting pairs). Inference rules (#16), each with an id and tests, and their results always tagged `INFERRED` with the rule: `RotationRule` in `garden` (`family-rotation-v1`: warns when a crop follows one of the same family in a plot; perennials are left out, #139). The sowing, planting and harvest calendars are rules on the curated files, not Cypher reads (#62): `ClimateCells` + `ClimateCellsReader` load `climate-cells-v1.csv.gz` (AgERA5 1996–2025 frost dates, growing season, land elevation and land fraction per 0.1° land cell of Europe, as compact primitive arrays); `KnowledgeValidator.validateCells` stops startup on a bad file; `FrostSeasonRule` (`frost-season-v1`) gives a `SiteProfile` its two safe months from `last_frost_p80` and `first_frost_p20`, after the altitude correction (6.5 °C/km, 0.15 °C/day, capped at 500 m, skipped on a coast with land fraction below 0.9 and when the altitude is missing or -9999); `ReferenceSite` gives the site of a zone named in the question (NORD = Milan, CENTRO = Vasto, SUD = Palermo, cell values with no correction); `FrostShiftRule` (`frost-shift-v1`) moves Vasto's curated CENTRO windows only where the site's safe months make them impossible, by crop `frost_group` (TENDER, HARDY, AUTUMN, OVERWINTER, LONG), never earlier in spring than Vasto, never reversing a window, year-round windows unchanged and winter harvests not derived when their shift is not 0; a window that cannot be derived is not a window, so the question escalates. `PestShiftRule` (`pest-shift-v1`, #162) moves the months a pest or disease is active on a crop (`pest-hosts.csv`, central Italy) as that crop's own calendar moves: from the crop's curated CENTRO windows it takes the one that starts earliest and the one that ends latest in the year (wrapping ones left out), adds the derived start's difference to the host row's start and the derived end's difference to its end (each clamped to two months, months clamped to 1-12 and a row never empty), and leaves the row as it is when it wraps over the new year, spans 11 months or more, the crop has no derived window at the site, or both differences are 0 (Vasto and Palermo). A moved row is INFERRED by `pest-shift-v1` with the curated row's sources (a row a member proposed is never moved, so it stays PROPOSED); the pest question of a garden (`GardenFacts.threats`, from `KnowledgeGraph.hosts`) reads the garden's site, and without a climate profile the curated months stay. `ClimateWindows.sowingFacts` (the SOW_NOW and SOW_IN_PLOT answers) leaves out the crops whose `use` is SERVICE (#140), while `windowFacts` still answers for their own calendar; `ClimateWindows` serves the derived windows and facts (with `rootology-editorial`, `agera5`, `copernicus-dem-90m`, plus `geonames-gtopo30` when the altitude was used); the curated NORD/SUD rows apply only when the question names that zone, and then win over the derived window of the same crop and activity; Vasto itself (CENTRO named, or the default outside a garden) gets its curated rows, not inferred ones. The Sources page shows the AgERA5, Copernicus DEM and GTOPO30 notices. `KnowledgeGraphLoader` writes curated windows only. Each sowing activity is its own fact (#112, `facts.SowingActivity`): `sowIn` (SOW), `seedbedIn` (SOW_SEEDBED), `transplantIn` (TRANSPLANT), `plantIn` (PLANT), `harvestIn` for HARVEST, `pruneIn` for PRUNE (#139, a perennial's pruning months, asked as `PRUNING_TIME`; a pruning window moves with its crop's frost group but never sets where the planting chain starts; an `OVERWINTER` pruning that starts before August moves only by how much the site's first safe month is later than Vasto's, `FrostShiftRule.VASTO_FIRST_SAFE`); Jev still chooses the months or crops, and `GardenPipelineAgent.activitiesOf` reads from the facts how each chosen value goes into the ground, so `PipelineAnswer.activities` (stored as `pipeline_run.activities_json`, Flyway `V34`) lets Claude's sentence (`ACTIVITIES_PROMPT`, only when present), the plain fallback and `AnswerCard` (values grouped by activity) say "in a seedbed February-March, transplant April-May" instead of one list; above a calendar answer `ui.CalendarVerdict` (#116) says what it means for the month of the question (the one it names, otherwise the month it was asked in), from the values alone, and a person's answer shows who answered instead of the confidence bar; golden cases check them with `expect.activities`. Companion pairs are never reversed. `KnowledgeGraph.resolve` finds a crop or organism by id, Italian, English or scientific name, and a name not found as written by its singular forms (`Singulars`, Italian and English endings, #108: questions say "i pomodori"); `factsAbout(name)` gives its facts in the question's language (subject kept exactly as asked), each as a `SourcedFact` with its source ids: declared companions/antagonists, `affects`, and `activeInSeason` from the pest months. `SourceCatalog` exposes `sources.csv`. `CropCatalog` loads the approved crops from the curated file `src/main/resources/knowledge/crops-v1.csv` (122 crops in 33 families, listed in `docs/crops-v1.md`: id, Italian, English and scientific names, family checked against Wikidata, Wikidata and FAO ECOCROP ids, `frost_group` for #62, `italian_article` so a sentence names the crop, "la fragola", #111, since #139 `lifecycle` ANNUAL or PERENNIAL with, for perennials only, `frost_hardiness` and its `hardiness_source`, and since #140 `use` FOOD or SERVICE (eight service plants and green manures, not food): the lowest air temperature an established plant stands, editorial and owner-reviewed, because ECOCROP's absolute minimum is where growth stops, not where the plant dies). `climate-cells-v1.csv.gz` is the climate profile file; `docs/climate-profile.md` describes it and how `tools/climate` makes it. Curated knowledge files (#16) live in `src/main/resources/knowledge/`: `sources.csv` (every source with license; only commercial-use sources), `crop-needs.csv` (FAO ECOCROP, imported by the `live-api` tool `EcocropImportTool`), `sowing-windows.csv` (the CENTRO rows are Vasto's, the base of `frost-shift-v1`, editorial, `verified=no`; the one curated NORD row applies only when the question names NORD), `crop-pairs.csv` (66 companion and antagonist pairs with an evidence level: study, extension or traditional; declared in one direction, never reversed), `pests.csv` (24 pests and diseases identified by EPPO codes; `other_names`, #140: common names loaded as global `Alias` nodes, so "lumache" finds the grey field slug; the validator refuses a name that is already a crop's or another pest's), `pest-hosts.csv` (affected crops and months, editorial, `verified=no`) and `pest-controls.csv` (#140: control methods per pest with kind, agent, evidence and sources; a SERVICE_PLANT row names the service crop in `agent`, checked against `crops-v1.csv`; loaded as `Control` nodes under their `Organism` by `CONTROLLED_BY`; `KnowledgeGraph.controlFacts` reads them as `controlledBy`, `controlKind` and `evidence` facts; `OrganismCatalog.isControlMethod` keeps the English method sentences out of the answer's badges). Human-readable versions: `docs/crops-v1.md`, `docs/crop-pairs-v1.md`, `docs/pests-v1.md`. `KnowledgeValidatorTest` covers the validator, `KnowledgeGraphTest` the loaded graph.
  - `decision`: `Intent` + `QueryKind`, `GraphFacts` (readings tagged CURATED / UNCONFIRMED / INFERRED, with source ids and, for inferred ones, `derivedBy`; Jev gets the INFERRED description only when an inferred reading is present, so suite requests are unchanged; the site's climate profile is never sent to Jev: the derived windows already account for its frost dates, and the dates made Jev doubt them, #62), `Decision`, interface `DecisionLayer`. `JevDecisionLayer` (TypeSafe System One API, structured state with fixed field order, `MIN_CONFIDENCE` 0.5) when `ROOTOLOGY_TYPESAFE_API_KEY` is set, otherwise `StubDecisionLayer`; `SkepticalStubDecisionLayer` as a baseline. Domain filter (#53): interface `DomainFilter`, `JevDomainFilter` (one Noul question, `is_garden_question`, on the question text alone as `state`, with `true`/`false` criteria; `REFUSE_BELOW` 0.15, a first value to review after the first live run) and `PassThroughDomainFilter` when no key is set. It decides whether a question is about vegetable gardens and small-scale growing; only a clear no is refused, and every failure (open circuit, error, timeout) lets the question through, marked as not judged (`Verdict.judged` false, also without a key), so the run says it went on unscreened (`GardenPipeline.Run.domainUnjudged`, #161) and the quality suite counts an off-domain question escalated during an outage as `FILTER_UNAVAILABLE`, not as a silent error.
  - `pipeline`: Embabel agent `GardenPipelineAgent` (Question -> Intent via Claude -> GraphFacts -> Decision -> Resolution -> PipelineAnswer, phrased by Claude). `GardenPipeline.ask(...)` never blocks (`ReviewMode.AUTOMATIC`); `start(question, noise, RunContext)` / `pending(spaceId)` / `respond(processId, spaceId, answer)` pause on escalation until a member of the run's space answers (`ReviewMode.HUMAN`). `respond` first claims the waiting question in one statement (`PendingEscalations.claim`, #152): a second person answering at the same time gets `AlreadyAnsweredException` before any call, and an answer that cannot be finished releases it. `NoisyFacts` / `NoiseProfile` degrade inputs for the suite. `FactScope` on the blackboard chooses the graph: `SUITE` (default: comparisons, recordings, `start`) or `KNOWLEDGE_BASE` (`GardenPipeline.askKnowledgeBase`, real questions). The domain filter (#53) runs in `GardenPipeline.start` only for `KNOWLEDGE_BASE`, after the guest check, the daily limit and the Claude circuit and before the agent process: a question refused as clearly off-domain costs no Claude call and no reviewer, is recorded in History with `off_domain` (Flyway `V24`; the row keeps its space, garden and the names snapshot), `rootology.questions{outcome=off_domain}`, and one `QUESTION` against the daily limit (it cost a Jev call); `askKnowledgeBase(question, context, askAnyway)` skips the filter once for the "Ask anyway" button, as a new question. `ask(...)`, `start(...)`, `respond(...)` and the resume after a restart never pass through it. The fixed text is `ask.offdomain` in the UI's language (no Claude call detected the question's), with `ask.offdomain.anyway` for the button. `PipelineAnswer.sources` lists the source ids of the facts behind the answer. Process ids are random UUIDs (`ProcessIdConfiguration`, `@Primary` `AgentProcessIdGenerator`, #61): Embabel's default draws a repeated "moby" name, and we key waiting questions, notifications and history by the id. Question kinds (#17): the suite's four plus `ANTAGONISTS`, `SOWING_TIME`, `HARVEST_TIME`, `PRUNING_TIME`, `SOW_NOW`, `CONTROL_METHODS` (#140: every method of a pest; a SUBSTANCE or MICROORGANISM adds the `READ_THE_LABEL` note, and Claude translates the methods, grouped by kind with their evidence) on the knowledge base, and `GROWING_NOW`, `PEST_RISK`, `SOW_IN_PLOT`, `PROPOSE_IN_AREA` on the asking space's garden (`GardenFacts`: `grows`, `threatens`, and `avoidIn` inferred by `family-rotation-v1`; source id `garden`; `RunContext` is on the blackboard, `RunContext.NONE` for suite runs). `PROPOSE_IN_AREA` (#141 step 2) is never read from a question: `understand` turns it into `OTHER` and drops any goals. The app builds it with `GardenPipeline.propose(question, intent, context)`: the area as subject, the month and one or two goals in `Intent.goals` (sent to Jev only when present, so every other request stays as it was). It skips understanding and the domain filter, counts one `QUESTION`, and is kept for the day in memory by area, month, goals and proposed crops, so asking again costs nothing. `GardenFacts.proposals` sends, per crop of `crop-proposal-v1` for that area, its window (tagged `frost-shift-v1` when derived) and `proposedFor`, `meetsGoal`, `uncertainty` derived by `crop-proposal-v1` (all but `EDITORIAL_WINDOW`, which the window's `rootology-editorial` source already says: sent again, it made Jev doubt nearly every proposal in the first real calls; the screen still shows it); Jev judges each crop, and an unsure area waits for a person like any question. An area that is not free has no facts and escalates. The screen is `ui.ProposalsView` (`/spaces/{id}/gardens/{id}/proposals`, contributors only), opened from the garden home's free-areas card: goal chips (one or two), one card per free area judged in the background, the crops Jev kept with their icons and a "?" for any uncertainty, "Plant" (asks first, records the planting today, and the area leaves the list), and the violet waiting edge when Jev is unsure.
  Question context (#55): one resolver, once per run, between understanding and the facts. The `ContextResolver` action gives a `QuestionContext` (internal to the pipeline) — the run's garden, the climate profile of the site its calendars read, the plot a `SOW_IN_PLOT` question names, the place of the forecast, the effective `Intent` and the context notes — and every part reads it: `GardenFacts`, `WeatherFacts`, `LightFacts`, the decision layer and the answer. A garden or plot named in the question (#57): inside a space, the understanding prompt also carries the names of the space's gardens and of the current garden's plots, as data (`ContextResolver.names`, quotes and control characters removed, at most 30 of 60 characters; none for `RunContext.NONE`, so the suite's prompt is unchanged), and `Intent.garden` is the garden named as written (dropped when the space has no garden; never sent to Jev). For the kinds a garden changes (`NEEDS_ZONE` and `NEEDS_GARDEN`) the resolver looks it up with `GardenService.gardenNamed` (the plots' rule: the same name ignoring case, otherwise a whole word of a single garden's name; a town is not a name): found, it replaces the page's garden, with the `GARDEN_OF_QUESTION` note when they differ, and the run's history, escalation and notifications belong to it; no match escalates before the decision layer (`the garden named is not clear`, `GARDEN_NOT_FOUND`) and keeps the page's garden, and several becomes the person's choice of garden (#107). The golden fixture `two-terraces-*` covers the named, unknown and ambiguous cases, and `GoldenVerdict` compares the garden strictly. A place named in the question (#107): the understanding prompt asks for `Intent.place` only for runs in a space (the block of #57 is then always present, even with no garden names; the suite's prompt is unchanged) and tells Claude to leave `zone` null when the question names a town. A place is used only by `SOWING_TIME`, `HARVEST_TIME` and `SOW_NOW`, and wins over the zone, the garden and the default: `ContextResolver` finds it with `GeoNames.search` and `GeoNames.elevation` (the population of `Place` decides: the exact name, case and accents ignored, Italy first, the most populous when it has at least ten times the second's population, otherwise the person chooses), and a place gets its own climate cell and altitude (`FrostSeasonRule.profile`, `ClimateFrom.PLACE`), its own forecast coordinates and, inside a garden, the `PLACE_OF_QUESTION` note. The calendar kinds ask the person to choose instead of escalating (`QuestionContext.choice`, kinds `PLACE` and `GARDEN`, reasons `MISSING`, `NOT_FOUND`, `AMBIGUOUS`): a calendar question outside a garden with no place and no zone (the distinct towns of the space's gardens), a place not found (the same towns) or matching several (the candidates), a `NEEDS_GARDEN` question outside a garden (the space's gardens) and a garden name matching several (the matches); a garden name matching none still escalates. A run with a choice makes no fact, no Jev call, no Claude phrasing, no escalation and no history row, counts as a question and as the metric outcome `choice`, and `GardenPipeline.Run` carries the choice, the intent, the place the run used (`QuestionContext.place`, the one named in the question or the one chosen) and the agent's process id, which the UI needs to offer a garden at that place and to open an answer continued in its own garden. `GardenPipeline.continueWith` runs the same question again with that intent and the chosen place (no second lookup) or garden (checked to belong to the space, contributors only): no understanding call, no domain filter and no daily limit, with usage recorded as `CONTINUATION` (Flyway `V32`). Precedence for the calendar kinds (sowing and harvest windows, `SOW_NOW`, `SOW_IN_PLOT`): a zone the question names uses that zone's reference site (`ReferenceSite`), otherwise the run's garden uses its own `SiteProfile` from its coordinates and altitude, otherwise the default is Vasto (CENTRO). `GardenService.zone` (≥44° N NORD, ≥41.5° N CENTRO, else SUD, `OUTSIDE_ITALY` abroad) is now only for the note that says the question names another zone than the garden's, and for a garden abroad with no profile; it no longer chooses the calendar. A garden abroad with a profile gets its derived windows and the `WINDOWS_FROM_CLIMATE` note; `OUTSIDE_ITALY` stays only for a garden abroad with no profile. A pest question (`PEST_RISK`) gets the month and no calendar note, since the pest months and the weather apply abroad too (#58); it does read the garden's site, because the pest months follow the crop's calendar (#162). The month is the question's, or the current month in Italy. Only the run's garden is read: nothing in the pipeline chooses a garden any more (no `findFirst` over gardens or plots). A plot is looked up in that garden only, and a plot not found or matching several and a garden deleted between opening the page and asking escalate before the decision layer, without a Jev call, with a note that says the specifics (`reason.gardengone`, `reason.plot`); a garden question asked outside a garden (`GROWING_NOW`, `PEST_RISK`, `SOW_IN_PLOT`) is the person's choice of garden (#107). At the space level general questions use the defaults with a note; `RunContext.NONE` (the suite) gets no note at all, so its requests stay as recorded. `ContextSnapshot` (space and garden names, the place when the question named one, the zone only when the question named one, the month with where it came from, plot, and the last and first frost with where the climate profile came from) is what `PipelineAnswer.context` carries, what `AnswerCard` shows above the answer (`ui.ContextText`: "Risposta per: Casa · Orto sul tetto · ultime gelate fine marzo (dall’orto) · novembre"; old rows without climate fields still show their zone), what History shows in its context column and what `pipeline_run.context_json` (Flyway `V23`) and `pending_escalation.context_json` store, so a resumed escalation shows the context of the question and a row stays readable after a refactor; rows stored before it have none. `Intent` also carries `language` (names and answer in the question's language; never sent to Jev), `zone` (NORD/CENTRO/SUD only when the question names one) and `month` (SOW_NOW, default the current month in Italy); for `SOW_IN_PLOT` its subject becomes the found plot's real name. Windows from `frost-shift-v1` reach Jev as INFERRED readings with their site's sources; the knowledge base's calendar rules tell Jev the facts are already those of the question's site.
  - Quality suite (#20): golden questions in `src/main/resources/quality/golden-questions.yaml` (question, expected intent, fixtures for garden, weather and space facts, expected answer set or escalation; the run is inside the case's garden, or at the space level when the case has none, #55), answers written by hand from the curated files and reviewed by the owner, never computed by the pipeline's code (`notes` are checked on answers and on escalations, #60). `GoldenQuestionsTest` runs them offline in CI (Claude mocked with the expected intent, stub decision layer, a fixed "today" through the `Clock` bean) and fails on any mismatch: silent wrong answer, missed or unexpected escalation, missing note.   - `experiments`: the quality suite's arbiter (`ExperimentRunner`), the five cases (`ExperimentCase`), recorded answers and comparison records.
  - `spaces` (#15): `app_user`, `space`, `space_member` (`OWNER` / `MEMBER` / `GUEST`), Flyway `V2__create_spaces.sql`, `V3__track_first_login.sql` and `V11` (GUEST, #33). A GUEST only looks: sees the garden, history, escalations and the space's knowledge, but asks nothing, changes nothing in the garden, answers no escalation and proposes no fact (`SpaceService.requireContributor` in the services, `CurrentUser.canContribute` hides the actions; answering an escalation also requires a contributor of the space). GitHub logins are stored and compared in lower case (`SpaceService.normalizeLogin`). `SpaceService.signedIn` (called on every login) creates the person's personal space on their first real login (`first_login_at`), also when someone had already added them to a space; `spacesOf`, `isMember`, `membersOf`, `addMember`, `leave` (a member's own choice; nobody leaves their personal space, `space.personal_of`; a space keeps at least one owner), `changeRole`, and `block`/`unblock` instead of removing (#105, Flyway `V35`: `space_member.blocked_at`/`blocked_by`; a blocked member stays listed with `Member.blocked`, but every check — `isMember`, `canContribute`, `spacesOf`, `membersForSystem`, `belongsToAnySpace` — treats them as not a member, their questions keep their name, and an owner is never blocked). A change of role, a block, an unblock and a leave publish `MembershipChanged` with an optional checked message (`SpaceService.checkedMessage`, 500 characters), which `notifications` stores as kind `MEMBERSHIP` (event, who acted in `asked_by`, the space's name then) for the member, or for the owners when someone leaves; email words it in Italian (`MembershipText`) and Telegram carries only what changed and the link. A display name (#106, Flyway `V36`: `app_user.display_name`, unique ignoring case, 2–40 characters, and `name_asked_at`): chosen freely in My account or in `ui.NamePrompt` at the first sign-in (skippable, asked once), never the same as another person's name or kept login (`SpaceService.chooseName`, `DisplayNameTakenException`); the login stays the key in every table and is what services take, while views show `CurrentUser.nameOf`/`namesOf` (members, history, waiting questions, answers' reviewer, proposals, notifications, the person menu; admin pages show name and login) and the email and Telegram digest read it through a join; a personal space still called after the login takes the name. Personal data elsewhere refers to a space by id.
  - `access` (#65, Flyway `V27__access_requests.sql`): invitation requests from people who are not users yet. A GitHub or Google sign-in that is not admitted (not in the bootstrap lists, in no space, no valid invitation) is no longer refused but becomes **pending**: the principal carries the authority `ROLE_PENDING` alone, its provider identity and the login it would have, and nothing is written (`AllowListOAuth2UserService`, `GoogleOidcUserService`, `SignInSteps.pendingAttributes`; the linking flow and every other refusal are unchanged). `AccessRouting` (a `VaadinServiceInitListener`) sends a pending person from any route to `/request-access` and lets them reach only `/sources`, `/privacy`, `/welcome`, `/logged-out` and `/invite/{token}` (where a pending person is shown the sign-in buttons, so signing in again with the invitation admits them); `WelcomeView` does not send a pending person Home, and `PublicLayout`'s link for them signs them out (Vaadin's `SecurityContextLogoutHandler` and a reload) onto the welcome page (#76), since "/" would only lead back to the request; an admitted person who opens the request page goes home, and `CurrentUser` treats a pending principal as a member of nothing. `AccessRequestView` (PublicLayout) shows one of: the motivation form (500 characters), the open request with Withdraw, the rejection with when they may ask again, the approval with sign out, or the daily cap; it also lists what is kept and is their export. `AccessRequestService` enforces one open request per identity (partial unique index on PENDING), `rootology.access-requests.daily-limit` (10, Italian time) and `rootology.access-requests.retry-after` (30 days); `AccessRequested` is what `notifications` listens to, so every admin gets an `ACCESS_REQUEST` row with no space (Flyway `V27` makes `notification.space_id` nullable for this kind) and the email digest and Telegram (`TelegramMessages`) say only that a request waits, with `/admin`; approved identities are admitted at their next sign-in, which creates the account and deletes the request in one transaction (`AccessRequestService.admitted`). Admins decide in the "Invitation requests" section of `AdminView` (motivation as plain text, confirmations, `decided_by`/`decided_at`). Retention (`rootology.retention.rejected-access-requests`, `pending-access-requests`), `AccessPersonalData` for export and account deletion, `docs/privacy.md` and `docs/security.md`. The motivation never reaches Claude or Jev and is never logged.
  - Invitations (#23, `InvitationService`, Flyway `V4`): an owner creates a single-use link (`/invite/<token>`, 7 days, optionally restricted to one GitHub login); only the token's SHA-256 is stored; owners list and revoke pending ones. - `tools/climate/` (#62): an offline Python tool, outside the Maven build and CI, that computes frost and growing season indices per AgERA5 cell (Copernicus C3S, 0.1°, daily) for the climate profile. Python 3.13 (Homebrew) in `tools/climate/.venv` with the pinned `requirements.txt`; working files in `tools/climate/work/` (both ignored by git); the CDS key in the owner's `~/.cdsapirc`, never in the repository. `agera5_frost.py years A B` downloads month by month (global files: no area parameter), crops Europe and keeps yearly indices (ETCCDI FD with TN < 0 °C, GSL, last and first frost); `combine A B --out` writes the CSV (median and 1-in-5-years dates). Periods: 1996–2025 for the app, 1991–2020 to check against the ISPRA normals. Cell altitude and land mask: `dem_cells.py tiles` reads the Copernicus DEM GLO-90 tiles (public bucket `copernicus-dem-90m`, licence read: free, commercial use allowed, with its notice) with `rasterio` and keeps per cell the mean land elevation and the land fraction (sea is 0 m in the DEM); `combine --dem` keeps cells with at least 25 % land and adds their elevation. A garden's altitude comes from GeoNames `gtopo30` (USGS, public domain; 1 km, imprecise on coasts, enough for windows moved by whole months), as described in `docs/climate-profile.md`.
